# withings-mcp - agent guide

`CLAUDE.md` symlinks to this file. It orients AI agents and contributors working *in* the code, and deliberately does not repeat the user-facing docs:

- **What it is, install, auth, tools, config, CLI, usage** -> [README.md](README.md)
- **Dev environment, running tests, pre-commit hook, PR & security process** -> [CONTRIBUTING.md](CONTRIBUTING.md)

**This is a public open-source repository and health data is sensitive PII.** Read the Data Safety Rules before committing.

## Data Safety Rules

Before committing ANY change, verify:

- **No real health measurements** in code, tests, commits, or docs - no real weights, sleep data, heart rates, blood pressure readings, SpO2 values, or body composition figures
- **No personal identifiers** - no real names, Withings user IDs, device IDs, MAC addresses, or dates of birth
- **No credentials** - no OAuth tokens, client secrets, API keys, or session data
- **Test fixtures**: always import from `tests/fixtures.py` factory functions - never hardcode values that could resemble real health data
- **Error messages and logs**: status codes and operation names only - never measurement values or API response bodies
- **`config/` and `*.db` are gitignored for a reason** - never override this
- **Before committing**: run `git diff --cached` and verify nothing resembles real user data

The `scripts/check-no-data.sh` pre-commit hook refuses `*.db` files with their journals and copies, `*.bak` and `*.backup` files, anything under the top-level `config/` except `.gitkeep` and paths ending in `.example` or containing `.example.`, any added, changed or renamed file over 100KB except the root `uv.lock`, and any path containing a newline. Install it per [CONTRIBUTING.md](CONTRIBUTING.md#install-the-pre-commit-hook); CI does not run it. **It matches paths and sizes and never reads contents**, so a secret in code passes, and so does a credential file outside `config/` or named like an example. None of the rules above is fully enforced by it; check them yourself.

## Architecture

- **Entry point**: `src/withings_mcp/cli.py` - routes `auth`/`sync`/`doctor` subcommands or starts the MCP stdio server. **Keep it inside the package.** An entry point of `main:main` needs `src/main.py`, which installs as a top-level `main` module in site-packages. Any other package doing the same overwrites it, and `withings-mcp` then starts that package's program instead
- **MCP server**: `mcp_instance.py` creates the shared `MCPServer("withings-mcp")` instance
- **Auth**: `auth.py` - OAuth with a 30-second inline code exchange in the callback handler, token refresh with a 5-min buffer. Redirect `http://localhost:8585`; scopes `user.info,user.metrics,user.activity`; access tokens 3h, refresh tokens 1 year. **The callback listener is `_CallbackServer`, not a bare `HTTPServer`, and that matters on Windows.** `HTTPServer` sets `allow_reuse_address`, which on POSIX only waives TIME_WAIT. On Windows it is consent to be displaced: per Microsoft's same-user table for a specific-address bind, a first socket holding the address with `SO_REUSEADDR` is bound over by a second one asking for the same, so another process could take the authorisation code. **Not asking is what closes it** - the same table shows a first bind with neither option refusing that second bind. `SO_EXCLUSIVEADDRUSE` is asked for as well because Microsoft recommends it for server sockets and because it is the half that would still hold for a wildcard bind, which this listener is not. Never ask for both: reuse requested after exclusive use is the configuration Microsoft calls insecure, and `allow_reuse_port` (the POSIX-side equivalent hazard) is pinned off for the same reason. The cost is that a Windows port stays held until the previous connection finishes closing. `setup_auth` catches the resulting `OSError` and binds before opening the browser. `TestTheCallbackPortIsNotShared` drives the Windows branch on a POSIX runner against a recording socket rather than reading the source for it - source assertions here let the option be set after the bind, at the wrong level, on the wrong socket or with a value of 0, all of which pass a check that only looks for the name
- **The credential files are the only copy of the tokens, but for a grant whose save failed.** `_refresh_token` reads the token file on every call and the client file on every refresh, and keeps nothing else between calls, because `withings-mcp auth` replaces them from another process while the server runs. Held in memory, the old token stays in use after `auth` until a restart. `refresh_token` serialises calls in a process with `_token_lock`, since two refreshes would spend the same refresh token and Withings rotates it on use; it is held across the refresh request, so a slow one holds every token request in the process for as long as the request takes. After a refresh the token file is read again: if its token is still valid and its `expires_at` later than the call started from, `auth` or another refresh saved it during the request, so it is used and nothing is saved. `_usable` is what decides; the comparison guards a clock that steps back during the request, which would otherwise make the untouched file look new. **Otherwise the refresh is saved, whatever the file holds**, because the refresh token just issued is known to be live and another copy's usually is not, and this package's writes replace the file atomically, so an unreadable file is gone or corrupt rather than half-written by it. **A server's refusal judges the refresh token sent and nothing else**: if the file now holds one other than that, or than the one a held grant replaced, its token is used when valid and otherwise the refusal is a `RefreshNetworkError`, so the next call refreshes from the file; a file still holding either of those is a `TokenRefused`, whatever else in it changed, and so is a refused held grant with the file gone, though another writer may be about to put a grant there, an exception to the classification rule below. **A grant whose save fails is held in `_unsaved`**, because the file's refresh token may already be spent: it is used, and the save retried, on each call while the file still holds the refresh token it held when the save failed, or cannot be read, and dropped as soon as the file holds any other refresh token or the held grant is itself refused. It is the one copy kept between calls, keyed to that refresh token rather than to the whole file. `api.post` answers a 401 on a data request by retrying, which reads the file again; it never forces a refresh. Pinned by `TestTheTokenFileIsTheOnlyCopy` in `tests/test_auth.py`, whose rewrites keep the file's length and mtime so a cache keyed on either fails it, and by `test_a_rejected_token_is_retried_with_the_token_file_as_it_is_now` in `tests/test_api.py`. **What this does not close**, across processes, which the lock does not reach: two processes refreshing at once both send the same refresh token, and the loser is refused if the winner's save has not reached it, which across hosts includes the file-sync delay; a write landing between the second read and the save is overwritten; another writer, such as a file-sync client writing in place, can expose a half-written file, which the first read reports as a refusal; a grant held after a failed save is lost if the process exits before a save succeeds, after which only `auth` repairs the file; while one process holds a grant, another reading the file finds the spent refresh token and is refused, until the holder's save succeeds on its next call; and while a grant is held, an older copy put in place by another writer, such as a backup restore or a file-sync client, holds a different refresh token, so the held grant is dropped and the next refresh is refused. A grant written on a host whose clock runs behind by more than an access token's lifetime less the buffer looks expired here and is saved over. `tests/test_auth.py` makes its own credential writes through `_refuse_unless_isolated`, which refuses any path outside the temp dir `_isolate_auth` created, so a fixture that did not run fails those tests before any file is touched; `test_the_credential_writer_refuses_outside_the_isolated_directory` pins the guard. It does not catch production code that stops reading `auth.WITHINGS_*_PATH`, and the other test files write to temp dirs of their own without it
- **Failure classification**: `refresh_token` is a boundary over `_refresh_token` and raises exactly two types. `TokenRefused` only where the server or the credential files judged the credentials unusable; `RefreshNetworkError` for everything else, via a catch-all, so an unanticipated failure lands there by construction rather than by listing exception types. `api.post` maps the first to `WithingsAuthError`, which `doctor` grades FAIL and answers with "run auth" - rewriting a token file other hosts may share - and the second to `WithingsAPIError`, which grades WARN. **Never widen `TokenRefused` to a condition that can clear on its own** (a rate limit, a 403 from a WAF, an unreadable response): that turns a transient fault into a rotated token on every host. Pinned by `TestTheRefreshBoundary` and `TestAgainstTheRealRefresh` in `tests/test_api.py`
- **API**: `api.py` - POST wrapper that handles Withings' status-in-body errors, typed exceptions
- **DB**: `db.py` - SQLite schema, insert/query helpers
- **Tools**: `tools/` - domain-grouped modules
- **Helpers**: `helpers.py` - value parsing, date coercion, formatting; `MEASURE_TYPES` and `WORKOUT_CATEGORIES` constants live here. **`require_auth` is also the one place an exception that escapes a tool keeps its message.** `mcp` 2.1 keeps a `ToolError`'s text and replaces every other exception's with `Error executing tool <name>`, so a `WithingsError` is converted and nothing else is. The split follows the Data Safety Rules: this package writes the messages it raises deliberately and keeps response bodies out of them, while an unplanned failure's text is what must not travel, since a filesystem error on the token file or the cache names an absolute path. **Never widen the conversion to `Exception`**: it would undo that in one line, and `test_an_unplanned_error_is_left_to_be_masked` is the half that fails if you do. The credential gate above it still *returns* JSON rather than raising, so a caller with no credentials gets an answer instead of a failed call. Pinned in both directions by `TestWhichErrorsAreExplainedToTheModel` in `tests/test_errors.py`, and structurally by `test_every_exception_this_package_defines_reaches_the_model` in the same file, which sees classes this package *defines* and not raise sites: a bare `RuntimeError` or `ValueError` raised here is masked and nothing reports it
- **Config**: env vars `WITHINGS_MCP_CONFIG_DIR`, `WITHINGS_MCP_DB_PATH`
- **Doctor**: `doctor.py` - the `doctor` subcommand. Every check is read-only and makes no API call, and two properties are load-bearing rather than incidental: it never opens the database through `db.get_db()` (which would create it and destroy the evidence for the wrong-path and stale-cache checks), and of this package it imports only `config` and `db` - never `auth` or `api`, so no code path can send the stored refresh token or rewrite the token file. Both are pinned in `tests/test_doctor.py`, the second by parsing this module's imports rather than by observing behaviour; keep them true when adding a check. **The permission findings are inert on Windows** - `os.access` there consults neither mode bits nor ACLs, so an unreadable database or an unwritable config directory cannot be reported at all, and the tests asserting them skip rather than being made to pass. A Windows database that is genuinely ACL-denied still reports, via the open-failure branch, which says the contents are not implicated - so the gap is a missing diagnosis, never a wrong one

## Database schema

SQLite at `withings.db` (gitignored). Tables:

- `body_measurements` - grpid-keyed body comp (weight, fat, muscle, bone, BP, SpO2)
- `sleep_summaries` - nightly sleep data (durations, HR, RR, score, snoring)
- `activities` - daily activity (steps, distance, calories, HR zones)
- `workouts` - individual sessions (type, duration, HR, calories)
- `sync_log` - sync history with timestamps and record counts

## Key patterns

- All tools are `async def` with `@mcp.tool()` + `@require_auth` decorators
- Sync HTTP calls wrapped in `anyio.to_thread.run_sync()` to avoid blocking
- Cache-first with a `live=True` flag for fresh API queries; `withings_get_heart` and `withings_get_devices` are always live; `withings_get_sleep(detail=True)` is live (minute-by-minute phases, capped at 7 days)
- Date parameters accept ISO dates, month strings, and relative days (e.g. "30d")
- **`withings_trends`' `data_type` and `period` are constrained in the annotation, so the server refuses before any body runs.** The class this closes is a wrong answer rather than bad input: unconstrained, `period` falls through `_get_period_key`'s trailing `else`, so an unrecognised value returns twelve months of correct **monthly** figures under `"aggregation": "<whatever was sent>"`. Real data, no error, nothing empty: the shape nothing looks at twice. **Do not move either check inside the tool.** An in-body check reaches only the caller who already made the call, while the schema is what a model reads before deciding what to send.
  - `TrendType` is unpacked from `_TREND_FNS` (`Literal[*_TREND_FNS]`), so the schema offers exactly the types there is a trend function for. `_COMPARE_QUERY_FNS` is a separate dict and has to hold the same types; that half is a real pin, and the `_TREND_FNS` half of `test_both_dispatches_answer_every_accepted_data_type` is tautological while the unpack stands. It earns its place against a hand-written list.
  - **The annotation does not stop a dispatch being mis-wired, and that relabels just as quietly.** Two entries exchanged answer the wrong question under the right label. The trend functions name their own type, so `test_every_accepted_data_type_answers_about_the_type_it_was_asked_for` sees it; compare mode writes `data_type` straight from its argument and cannot, so `test_compare_mode_summarises_the_type_it_was_asked_for` counts rows against a cache holding a different number of each.
  - `TrendPeriod` has no dispatch to unpack, so the property is pinned instead of the list: `TestEveryAcceptedPeriodBucketsDifferently` fails if a value is added to it and not to `_get_period_key`, which is the same defect one line along, and the bucket keys are asserted for shape as well as the echoed label.
  - The docstring's `Options:` lists restate the same enums and are read back by `TestTheDocstringOffersWhatTheSchemaAccepts`; the README says it again in prose and is not pinned at all.
  - **A default is never validated**, so it is the one route back to the defect that no refusal test can see: pydantic checks what a caller sends and not what the signature falls back to. `test_the_defaults_are_values_the_schema_accepts` reads both defaults off `inspect.signature` and checks them against the enum and against the value the docstring quotes.
  - All of it in `tests/test_argument_validation.py`. Its tool calls go through `mcp.call_tool`, the only layer that applies the schema, so a test calling the function directly passes whether the constraint is there or not; the rest read the docstring, the registry, the signature or the dispatches. **Every guard in that file has a pin of its own** in `TestTheChecksHereHoldTheirOwnGround`, because each one reverts in a single edit with the suite still green: the row counts must differ or a summary of the wrong table looks right, the `Options:` to `Default:` narrowing must stay or a dropped option hides in the default, the empty string must stay excluded from the message match or any reply counts as a refusal, and the bucket-key shapes must stay mutually exclusive or the oracle stops discriminating without failing
- **An open filter is checked against the vocabulary this package names.** Without the check, a `metrics` list naming no known metric for `withings_get_body`, or a mistyped `category` for `withings_get_workouts` comes back as an empty answer, which reads as a period without data rather than as a filter that cannot be used. Withings defines both sets and `MEASURE_TYPES` and `WORKOUT_CATEGORIES` hold the names, so the accepted values are a list this package can state rather than whatever a cache happens to hold. Both refusals raise `UnknownFilterValue`, which `require_auth` converts so the message survives on the wire. **The two messages name different things on purpose.** The metrics are few enough to list, so the refusal lists them; the categories are not, so it names the ones the cache holds, which is what a caller can act on, and the tool's docstring carries the full list because that is what a model reads before calling. `test_the_documented_categories_are_the_ones_the_server_can_produce` compares that list against the constant rather than trusting it, and the blank line that ends the `Options:` block is what its extractor stops at. **An empty filter is refused too**, since every name contains the empty string and reading it as no filter answers a narrower question with everything. **The category check returns the normalised value and the query layers use that**, because the three folds are not the same one: this check, the SQL `LOWER(...) LIKE` on the cached path and the `.lower()` on the live one. Normalising privately and passing the caller's raw string accepts `" cycling "` and then matches nothing. `query_workouts` escapes the pattern as well, since `_` is a LIKE wildcard and a real character in `horse_riding`, so an unescaped one answers with every workout. **A group holding none of the metrics asked for is dropped by value, never by key**: a cached row is `SELECT *`, so every metric column is present as a key and a blood-pressure group still carries `weight_kg`. A key test therefore looks right and drops nothing. All of it in `tests/test_filter_arguments.py`, whose calls go through `mcp.call_tool`
- All logging to stderr (stdout reserved for JSON-RPC); error messages carry status codes only, never health values
- **Every datetime conversion names a zone.** The Withings API speaks epoch seconds and this server stores ISO dates, so a naive `fromtimestamp` or `combine` silently reads the machine's zone and moves a date by a day. `doctor.py:_timestamp_or_none` is the single exception, deliberately, because it prints a token expiry for whoever is reading the terminal. A source-reading test in `tests/test_query_tools.py` requires the zone everywhere else and exempts that one by function name, so moving it fails the test rather than widening the exemption. The test exists because the behavioural guard - running the suite under a forced western zone - needs `time.tzset`, which Windows does not have

## Seams the suite does not cross

Nothing in the suite fails if these break, so check them by execution when they change.

- **The pre-commit guard.** `scripts/check-no-data.sh` is not run by any test or by CI. To check a change to it, work in a throwaway clone: stage one probe per class it should refuse, plus one it should pass, using `git add -f` for gitignored paths, and compare the script's exit code with what you expect.
